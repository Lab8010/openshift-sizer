# OpenShift 4.22 サイジング（OpenShift Virtualization）

> **免責事項**：本ツールは有志が作成した非公式のサイジングツールです。環境固有のワークロード特性などは判定できないため、本ツールから得られる情報はあくまで参考としてご利用ください。最終的な構成は、Red Hat の公式ドキュメントと実環境での検証に基づいて判断してください。

**公開版**：https://lab8010.github.io/openshift-sizer/

OpenShift Virtualization 上で動かすゲスト VM の台数と仕様から、コントロールプレーン・コンピュート・インフラの各ノードについて、CPU・メモリ・ストレージ・ネットワークの必要量と確認条件を求めるブラウザアプリです。結果は、根拠と前提を含む日本語の A4 レポートとして PDF に保存できます。

- 対象：OpenShift Container Platform 4.22、OpenShift Virtualization 4.22。コントロールプレーン、コンピュート、インフラを分けた通常のマルチノード構成
- 適用範囲外：SNO、コンパクトクラスタ、Hosted Control Planes、ODF 自体の構成設計
- 入力・計算・ファイル作成はすべてブラウザ内で行います。バックエンドはなく、入力値を外部へ送信しません（入力はこのブラウザの localStorage にだけ保存します）。

## 必要なもの

- Node.js 20 以降（24 で確認）
- npm

## 起動・ビルド・テスト

```bash
cd openshift-sizing
npm install          # 初回のみ
npm run dev          # 開発サーバー（http://localhost:5173）
npm test             # 自動テスト（Vitest）
npm run build        # 型チェック + 本番ビルド（dist/ に出力）
npm run preview      # ビルド結果の確認（http://localhost:4173）
```

`dist/` は相対パスで出力するため、任意の静的 Web サーバーに置いて使えます。

### URL パラメーター（確認用）

| パラメーター | 動作 |
| --- | --- |
| `?mode=detail` | 詳細入力で起動する |
| `?view=wizard&step=N` | 簡易版の N 問目を開く |
| `?sample=1` | サンプル案件を読み込み、簡易版の結果を開く（`mode=detail` と併用で詳細入力のサンプル） |
| `?sample=large` | 詳細版の、複数ページになる大きなサンプルを読み込む |
| `?view=report` | 印刷用ビューを直接表示する（`sample` と併用可） |
| `?tab=result` | 結果タブを開いて起動する |
| `?view=network&netview=result` | ネットワーク診断の結果を開く（`netview` は intro／wizard／result／patterns／learn） |
| `?net=sample` | ネットワーク診断のサンプル回答（パターン C、SR-IOV の検討あり）を入れる |

## 使い方

画面は Network Advisor（OpenShift VM Network Advisor）と同じ構成です。上部のメニューで「サイジング」「詳細入力」「前提・出典」を切り替えます。

### サイジング（簡易版・既定）

トップの「サイジングをはじめる」から、8 つの質問に選択式で答えます（うち 2 問は任意）。

1. VM のサイズと台数：目安サイズ（S・M・L・XL）ごとに台数を入れるか、カスタムサイズを追加します
2. CPU の共有度合い（CPU 割り当て比率 1:1〜10:1）
3. 物理サーバ 1 台の大きさ（目安の仕様から選ぶか、数値を入力）
4. 物理サーバの台数（決まっていれば入力、決まっていなければ必要台数を計算）
5. 何台止まっても動かし続けたいか（N+0〜N+2）
6. インフラノードを分けるか
7. クラスタの規模（Namespace 数、任意）
8. ディスクを何重に保存するか（物理容量係数、任意）

結果画面には、判定（例:「物理サーバ 5 台で収まります（必要 3 台）」）、VM 用サーバ・コントロールプレーン・インフラノードの目安、「なぜこの台数か」、「OpenShift 基盤の要件」（etcd 用ディスク、コントロールプレーンの障害許容、イメージレジストリ、監視の保存量、ロードバランサー・DNS・NTP）を表示します。数値の内訳、前提と仮定、導入前に確認すること、計算の内訳、出典は折りたたみで開けます。

目安サイズ（S〜XL、サーバの仕様）と、簡易版で尋ねない値（常駐 Pod の要求量、ハード Eviction しきい値）はこのアプリの仮定です。結果の「前提と仮定」に明示し、仮定値はそこで変更できます。計算そのものは詳細入力と同じロジックです。

「詳細入力で見積もる」を押すと、簡易版の回答を詳細入力に取り込めます。

### ネットワーク診断

上部メニューの「ネットワーク診断」（またはトップの「ネットワーク構成を診断する」）から、VM のつなぎ方を選択式で答えます（5〜10 問）。OpenShift Virtualization で必要なネットワーク構成（パターン A〜D、修飾 E：マルチホーム、例外枠 F：SR-IOV）を診断し、構成図・理由・チェックリスト・サンプル YAML を出します。「パターン一覧」と「解説・用語集」もここから開けます。

診断結果はサイジングと次のように連携します。

| 診断結果 | サイジングへの反映 |
| --- | --- |
| すべてのパターン | サイジング結果の「ネットワーク構成」と PDF レポート（2 章）に要約を表示し、前提に記録する |
| パターン C・D（物理 VLAN へ出る） | 「導入前に確認すること」に、VLAN を物理サーバの NIC へトランクで出す確認を追加 |
| E（マルチホーム） | 追加 NIC 用のネットワークの確認を追加 |
| F（SR-IOV を検討） | サイジング結果で SR-IOV を使う VM とデバイス数を選ぶと、VM の追加メモリ（1 デバイスあたり 1,024 MiB）を計算に含め、配置を要個別評価にする |

ネットワーク診断は、別プロジェクトの OpenShift VM Network Advisor を `src/network/` に取り込んだものです。

### 詳細入力

1. 「入力」タブで、案件とクラスタ、VM プロファイル、候補ノードを入力します。VM プロファイルは台数・vCPU・RAM・ディスクの基本項目だけで、総 vCPU、VM メモリ要求量、永続ディスク論理容量を計算します。
2. CPU・デバイス、ストレージ性能、通信は、各 VM 行の下の「詳細」を開いて入力します。
3. 空欄は「未入力」として扱い、0 や既定値に置き換えません。該当しない項目は「対象外」と入力します（入力欄の候補からも選べます）。
4. 入力エラーは画面上部の一覧に表示されます。メッセージを押すと該当欄へ移動します。
5. 「結果」タブで、ノード別サマリー、前提と仮定、未確認事項、計算の内訳、出典一覧を確認します。各行の「内訳」で式・入力値・出典を表示します。

## PDF の保存手順

1. 画面右上の「印刷／PDF 保存」を押します。印刷用ビューに切り替わり、ブラウザの印刷ダイアログが開きます。
2. 送信先（プリンター）で「PDF に保存」を選びます。
3. 用紙サイズを「A4」、倍率を「100%（既定）」にします。余白は「デフォルト」のままにします。
4. 「ヘッダーとフッター」はオフを推奨します（オンにするとブラウザが URL と日時を余白に印刷します）。
5. 保存します。印刷用ビューから入力画面へは「← 入力画面に戻る」で戻れます。

レポートには、案件名、計算日時、製品バージョン、入力と前提、ノード別サマリー、容量・性能・帯域の内訳、未確認事項、出典一覧（クリックできるリンクと URL 文字列）を掲載します。状態は記号と文字（○ 適合、× 不適合、？ 未確認 など）でも示すため、モノクロ印刷でも読めます。

Chrome 158（ヘッドレス印刷を含む）で確認しています。コマンドラインからは次の方法でも PDF を作れます（macOS の例）。

```bash
npm run build && npx vite preview --port 4173 &
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new \
  --no-pdf-header-footer --virtual-time-budget=5000 \
  --print-to-pdf=report.pdf "http://localhost:4173/?sample=1&view=report"
```

## GitHub Pages への公開

`main` ブランチへ push すると、GitHub Actions（[.github/workflows/pages.yml](.github/workflows/pages.yml)）がテストとビルドを実行し、`dist/` を GitHub Pages へデプロイします。リポジトリの Settings → Pages で、Source を「GitHub Actions」にしておきます。ビルドは相対パス（`base: './'`）のため、リポジトリ名が変わっても設定変更は不要です。

## JSON の保存と読み込み

- 「JSON を保存」で、`schemaVersion`、製品バージョン、入力モード（`mode`）、全入力、ネットワーク診断の回答（`network.answers`）、保存時の結果、出典 ID と公式 URL を含む JSON を書き出します。簡易版では簡易版の入力（`simple`）も含み、読み込むと簡易版として復元します。
- 「JSON を読み込む」では、形式・単位・入力値を検証してから、現在の計算ロジックで結果を再計算します。保存時の結果は参考として扱います。形式や入力値が不正な場合は読み込まず、現在の入力を保ちます。

## 構成

```
src/
  domain/              計算・出典データ（React に依存しない純粋関数）
    sources.ts         公式参照データの唯一の登録場所（出典 ID・章節・URL・値・単位・適用条件・種類）
    types.ts           入力モデルと初期値
    parse.ts           入力の検証と正規化（未入力・対象外・0 の区別、単位変換）
    units.ts           単位変換（1 GiB = 2^30 bytes、1 GB = 10^9 bytes、1 Mbps = 10^6 bit/s）
    result.ts          結果の型と表示文字列（画面・印刷・JSON で共通）
    calc/              VM、コンピュート、コントロールプレーン、インフラ、サービス、ストレージ、ネットワーク、配置
    sample.ts          サンプル案件（サンプル値）
    simple.ts          簡易版の入力モデル、目安サイズ、詳細版の入力モデルへの変換
    simpleView.ts      簡易版の結果表示（判定・カード・なぜこの台数か・確認事項）
    networkLink.ts     ネットワーク診断とサイジングの連携（要約・確認事項・回答の検証）
  network/             ネットワーク構成診断（質問・パターン・用語集・YAML テンプレート・診断ロジック・画面）
    jsonio.ts          JSON のエクスポート・インポート
  ui/                  画面（Tailwind の簡易版ウィザード・結果、詳細入力、印刷用レポート）
  App.tsx              画面全体
tests/                 自動テスト（sizing、simple、networkLink、network/ 以下はネットワーク診断）
```

画面、印刷用ビュー、JSON は同じ `calculateSizing()` の結果を使います。表示文字列もこの関数の中で 1 回だけ作るため、3 つの出力の数値は一致します。

## 出典データの更新方法

公式値はすべて `src/domain/sources.ts` に登録しています。画面や帳票に数値を直接書いていません。

1. 更新する値を、URL に `/4.22/`（または対象バージョン）を含む Red Hat 公式資料で確認します。他バージョン、第三者ブログ、検索結果の数値は使いません。
2. 値は次のいずれかを編集します。
   - `SOURCES`：資料（出典 ID、製品・版、資料名、章節、URL）
   - `OFFICIAL`：個別の公式値（`sourceId`、`section`、`value`、`unit`、`kind`、`condition`）。`kind` は `official_min`（公式最低要件）、`official_rec`（公式の推奨・試験値）、`official_default`（公式の既定値・近似値）のいずれか
   - `CP_SCALE_ROWS`／`INFRA_SCALE_ROWS`：試験結果の表（自動参照に使わない行は `autoSelectable: false`）
   - `OFFICIAL_NOTES`：数値でない公式の確認事項
3. 章節アンカー（`#...`）は、実際に遷移できることを確認した場合だけ URL に付けます。確認していない場合は章ページの URL と章節番号を使います。
4. バージョンを変える場合は、`PRODUCT` と各 URL を合わせて更新し、`types.ts` の `SCHEMA_VERSION` の扱い（旧 JSON の互換性）を検討します。
5. `npm test` を実行します。テストは、結果で使った出典 ID がすべて登録済みで、URL が `/4.22/` を含むことを確認します。

## 計算の要点

| 項目 | 内容 | 出典 |
| --- | --- | --- |
| VM メモリ | ゲスト RAM + (0.002 × 要求メモリ + 218 + 8 × vCPU + 16 × グラフィックス + 1024 × (SR-IOV + GPU) + 256 × SEV + 53 × TPM) MiB。最大同時稼働台数で集計 | VIRT-INSTALL §4.2.4.1 |
| VM CPU | 共有：vCPU ÷ vmiCPUAllocationRatio、専用：1 対 1。比率がない場合は未算出（1 対 1 の計画値は明示選択時のみ） | VIRT-VM §8.18.14、VIRT-INSTALL §4.2.4.2 |
| Allocatable | max(0, 容量 − システム予約 − ハード Eviction しきい値)。既存クラスタの入力を優先。システム予約は公式の自動計算式（手入力で上書き可） | OCP-NODES §6.12.1 |
| Virtualization の追加分 | Worker 1 台あたり約 2 コア・360 MiB、インフラ群全体で約 4 コア・2,179 MiB（1 回だけ）、インフラ 1 台あたり約 150 MiB、各ノードのディスク約 10 GiB | VIRT-INSTALL §4.2.4 |
| コンピュート台数 | max(ceil(CPU ÷ VM 用 CPU), ceil(メモリ ÷ VM 用メモリ), Pod 枠, 2 台) から始め、平常時・停止時の簡易配置と移行用予備メモリ（別シナリオ）を満たす最小台数 | OCP-INSTALL、VIRT-INSTALL §4.2.7 |
| 試験表 | 比較台数と Namespace 数の両方が収まる最小の行（補間・外挿なし）。範囲外は要個別評価 | OCP-SCALE §2.1.2、§2.3.1 |
| ストレージ物理容量 | (論理容量 + スナップショット・増加量) × 物理容量係数 ÷ (1 − 空き容量比率)（このツールの試算式） | — |
| OpenShift 基盤の要件 | etcd 用ディスク（専用 SSD／NVMe、p99 fsync 10 ms 未満、8 KB 同期書き込み 50 IOPS 以上、容量はクォータ既定 8 GiB 超・最大 32 GiB）、コントロールプレーンの障害許容（3 台で 1 台）、レジストリ 100Gi 以上（2 レプリカ以上は RWX）、Prometheus の保存量の参考値（全ノード数で試験行を選択、200 ノード超は要個別評価）、ロードバランサー・DNS・ポート・NTP | OCP-ETCD §2.1–2.3、OCP-ETCD-PERF §3.2・§3.6・§3.11、OCP-INSTALL §1.3.4–1.3.6・§1.17.3.1、OCP-SCALE §2.3.2.1 |
| 移行帯域 | 総転送 bytes × 8 ÷ 目標秒数 ÷ 10^6。メモリ容量だけの場合は理想下限として表示し、実効帯域は未確認 | VIRT-MIG §11.1–11.2 |

## 残る制約

- 配置は同一仕様ノードへの簡易な分散配置です。NUMA、アフィニティ、SR-IOV・GPU 等の特殊デバイス、配置制約がある場合は「要個別評価」とします。
- コンピュートに置くサービスとインフラ分の要求量は、ノードへ均等に差し引いて配置を評価します。
- Prometheus の保存量は、入力された実効保存量から概算します。時系列数・収集間隔からの自動計算はしません。
- 個別プラットフォームのサポート可否、CPU 仮想化拡張の有無は判定しません（確認先の公式資料を表示します）。
- 公式試験値は特定の試験条件（AWS 上の cluster-density 試験など）の参考点です。Operator 数やオブジェクトの更新負荷で必要量は変わります。
